# ORP Bandwidth And Cost Analysis

These estimates assume:

- `riblt` object frames are used for debugging and demos
- production deployments prefer binary frames for lower overhead
- `symbolSize = 64`
- `batchSize = 32`
- one side needs about `1.35 * Δ` coded symbols to decode a symmetric difference `Δ`
- ORP usually budgets for both sides to transmit, so wire cost is approximated as `2 * 1.35 * Δ`

## Useful Approximations

### Binary `riblt` cost

For `symbolSize = 64`, one coded symbol is approximately:

- `count`: 4 bytes
- `hash`: 16 bytes
- `symbol`: 64 bytes

Total per coded symbol: about `84` bytes, plus a small frame header.

### Inventory phase

If `m` documents differ, inventory reconciliation sees a symmetric difference of roughly `2m` because each side holds a different `(docHandle, summaryHash)` entry for the same document.

Approximate wire cost:

```text
inventory_bytes ~= 2 * 1.35 * (2m) * 84
```

### Per-document repair phase

If a document has `d` missing or extra operation ids in total, the repair cost is:

```text
doc_repair_bytes ~= 2 * 1.35 * d * 84
```

This excludes the actual blob transfer for the missing operations.

## Scenario Estimates

### Mostly in sync

- visible docs: `10,000`
- differing docs: `25`
- differing ops per differing doc: `12`
- average blob size per operation: `220` bytes

Inventory:

```text
2 * 1.35 * 50 * 84 ~= 11.3 KB
```

Per-document repair:

```text
25 * (2 * 1.35 * 12 * 84) ~= 68.0 KB
```

Blob transfer:

```text
25 * 12 * 220 ~= 64.5 KB
```

Total rough wire budget: about `144 KB`

### Moderate divergence

- visible docs: `10,000`
- differing docs: `250`
- differing ops per differing doc: `40`
- average blob size per operation: `220` bytes

Inventory:

```text
2 * 1.35 * 500 * 84 ~= 113.4 KB
```

Per-document repair:

```text
250 * (2 * 1.35 * 40 * 84) ~= 2.27 MB
```

Blob transfer:

```text
250 * 40 * 220 ~= 2.10 MB
```

Total rough wire budget: about `4.48 MB`

### Severe divergence

- visible docs: `10,000`
- differing docs: `1,000`
- differing ops per differing doc: `1,000`
- average blob size per operation: `220` bytes

Inventory:

```text
2 * 1.35 * 2,000 * 84 ~= 453.6 KB
```

Per-document repair:

```text
1,000 * (2 * 1.35 * 1,000 * 84) ~= 226.8 MB
```

Blob transfer:

```text
1,000 * 1,000 * 220 ~= 220.0 MB
```

Total rough wire budget: about `447 MB`

At this point, snapshot transfer becomes the important escape hatch.

## Storage And CPU Considerations

### Per-document metadata

Each document summary stores:

- `docHandle`
- optional `basisSnapshotId`
- `tailCount`
- four 128-bit digest accumulators

That is typically a few dozen bytes of structured metadata before transport encoding.

### CPU cost

ORP saves wire bandwidth when differences are sparse, but a peer still needs to:

- materialize the visible document summary set for each session
- materialize the operation id set for each differing document
- seed those ids into `riblt`

That means:

- inventory CPU is roughly linear in visible document count
- repair CPU is roughly linear in operation count for each repaired document

ORP trades feed maintenance and Merkle maintenance for fresh set construction at sync time.

## Practical Guidance

- Use binary `riblt` frames in production. Object frames are convenient but noticeably larger.
- Keep `docHandle` and `opId` short and stable.
- Add snapshots for documents with long tails or chronic divergence.
- Bound `recentSnapshots` to a small list, such as `3` to `5`.
- Prefer ORP when most documents are already in sync and sparse repair is common.

## Summary

For thousands of documents and thousands of operations per document, ORP is economical when divergence is sparse or localized. It becomes expensive when many documents have large tail differences, and that is the point where snapshot compaction should take over.
